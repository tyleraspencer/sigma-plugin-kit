# The plugin harness

How a skill in this repo reaches a user. Three manifests and two delivery
paths, none of which are interchangeable.

## The manifests

| File | Read by | Purpose |
|---|---|---|
| `.claude-plugin/plugin.json` | Claude Code | Declares this repo as a plugin; `skills: "./skills/"` is what makes every `skills/<name>/` discoverable. |
| `.claude-plugin/marketplace.json` | Claude Code | Declares this repo as a *marketplace* so it can be added by URL. The `plugins[].source.url` must be the repo's real clone URL. |
| `.cortex-plugin/plugin.json` | Cortex Code | Same role as `plugin.json`, separate file because Cortex looks in a different directory. |

Bump `version` in all three together. They are separate files by necessity,
not by design, and a mismatch is invisible until someone installs a stale one.

Installing from a clone during development:

```
/plugin marketplace add /path/to/sigma-plugin-kit
```

## The .cortex/ mirror

Cortex Code auto-discovers skills from `.cortex/skills/<name>/SKILL.md`.
Upstream `sigma-agent-skills` symlinks that file at the canonical copy, which
is a Windows-checkout footgun: symlinks need `core.symlinks=true` plus
Developer Mode or admin, and without them git checks out a plain text file
containing the link *target* instead of the content.

So the mirror holds real, checked-in copies, regenerated by:

```bash
python3 scripts/sync-cortex-mirror.py
```

Run it after any edit under `skills/`, before committing. CI enforces it with
`git diff --exit-code .cortex/`, so drift fails the build rather than shipping
a skill whose Cortex copy is a version behind.

The mirror carries `SKILL.md`, `reference/`, and `examples/`. It deliberately
does **not** carry `scripts/` — executable tooling stays at the repo's own
`scripts/`, so there is exactly one copy to maintain.

## Delivery: ZIP vs. mounted clone

Claude Code auto-discovers `.claude/skills/` from a mounted folder. **Cowork
does not.** A Cowork user uploads a personal-skill ZIP at
`claude.ai/customize/skills` instead, and that upload is what makes a skill
auto-trigger in a Cowork session.

```bash
bash scripts/package-skill.sh <skill-name>
# -> dist/<skill-name>-<short-sha>.zip
```

With no argument it packages the sole skill under `skills/`, erroring if there
is more than one. `skills/_template/` is never auto-selected (leading
underscore) but can be packaged by name, which is how CI smoke-tests the
harness.

Every ZIP gets a `_PACKAGED_FROM.txt` stamped at the top level of the skill
folder, recording the git short SHA and UTC packaging time. That stamp is the
only thing that makes it visible later that an uploaded ZIP has drifted from a
since-updated clone — and with two live copies of a skill, silent drift is the
default failure. The stamp is removed from the working tree on exit, even on
failure.

**Both delivery paths matter at once, not as alternatives.** The ZIP supplies
the skill's instructions and scripts; a mounted clone supplies the working
directory where per-project state lives. Rebuild and re-upload the ZIP after
any change under `skills/`.

## Adding a skill

1. `cp -r skills/_template skills/<your-skill-name>`
2. Write the frontmatter. The `description:` is the entire activation
   mechanism — Claude decides whether to load the skill from that string and
   nothing else. Lead with `Use when…` and real trigger phrases; name the
   concrete artifacts; state prerequisites; say what it does *not* cover if a
   near-neighbour skill exists.
3. Keep the body to what must be in context on every activation. Push
   anything long or lookup-shaped into `reference/`.
4. `python3 scripts/sync-cortex-mirror.py`
5. `bash scripts/package-skill.sh <your-skill-name>` and upload, if Cowork
   needs it.
6. Test activation in a fresh session. If the skill doesn't fire, the
   `description:` is almost always the cause.

CI checks that every `skills/*/SKILL.md` has both `name:` and `description:`
in its frontmatter — a skill missing `description` installs cleanly and then
never activates, which is a slow failure to diagnose by hand.
